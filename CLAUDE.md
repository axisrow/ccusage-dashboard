# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

Почасовой дашборд расхода Claude Code и Codex в долларах (self-contained HTML,
только stdlib, без зависимостей). Токены — плохой прокси для денег: у разных
типов (input/output/cache-write/cache-read) цена различается в десятки раз,
поэтому дашборд считает именно стоимость, а не объём.

Причина существования — `ccusage` не даёт нужных разрезов (почасовая шкала +
проект + агент одновременно) и сканирует все логи целиком независимо от
`--since` (49 с против ~1.3 с у своего парсера).

Нет git-репозитория в проекте — это плоская директория скриптов, не
инициализированная как репо.

## Команды

```bash
./pricing.py --refresh                       # собрать ставки моделей (нужно один раз / при новых моделях)
./report.py --since 20260801 --open          # дашборд за период, открыть в браузере

./report.py --since 2026-08-01 --until 2026-08-03 --out dash.html
./report.py --since 20260801 --tool codex    # только один инструмент (--tool можно повторять)

./parse.py --stats                           # сводка в терминал, без HTML
./parse.py --since 20260801 --json           # плоские записи в JSON

./pricing.py --show                          # текущие ставки и их источник
./verify.py --since 20260802 --until 20260803   # сверка с ccusage (медленно, минуты — вызывает ccusage подпроцессом)
```

Даты — `YYYYMMDD` или `YYYY-MM-DD`, границы включительно. Никакой системы
сборки, тестов или линтера нет — файлы исполняемые (`chmod +x`), запускаются
напрямую через shebang `#!/usr/bin/env python3`.

## Архитектура

Конвейер: `parse.py` (сбор) → `pricing.py` (ставки) → `report.py` (агрегация +
рендер). `verify.py` использует `parse` и `pricing` как библиотеки для сверки
с `ccusage`.

- **`parse.py`** — параллельный парсер (`ProcessPoolExecutor`, до 8 воркеров)
  логов `~/.claude/projects/**/*.jsonl` и `~/.codex/sessions/**/rollout-*.jsonl`.
  Каждая запись превращается в `Row` (`NamedTuple`): час, инструмент, модель,
  агент, проект, 4 типа токенов. `collect()` — главная точка входа как
  библиотека, возвращает `list[Row]`.

- **`pricing.py`** — таблица ставок `dict[model] -> Rates`, кэшируется в
  `rates.json`. Источники ставок, в порядке приоритета (см. `NO_FIT`,
  `from_litellm`, `fit_rates`):
  1. LiteLLM (`fetch_litellm`) — с учётом TTL кэша (1h дороже 5m).
  2. МНК-подгонка из `ccusage` (`fit_rates`) — только для моделей вне LiteLLM,
     **никогда** для моделей Anthropic (`NO_FIT`), там подгонка даёт абсурд.
  3. `$0` — только если нет цены в LiteLLM И `ccusage` стабильно (3+ дня)
     отдаёт ноль. Модель без прайса не считается бесплатной: её объём уходит
     в отдельную строку «без прайсинга», а не смешивается с `$0`.

- **`report.py`** — строит JSON-payload (`build_payload`, `build_dimension`)
  по четырём измерениям (`DIMENSIONS`: tool/model/agent/project) и вшивает его
  в `TEMPLATE` (строковый HTML/JS с Chart.js через CDN — единственная внешняя
  зависимость, и та браузерная, не Python). Серии ограничены `MAX_SERIES` (=
  длина `PALETTE`), остальное схлопывается в «Прочее». **Порядок цветов в
  `PALETTE` менять нельзя** — он подобран для различимости при дальтонизме и
  обеспечивает разделение соседних серий.

- **`verify.py`** — гоняет `ccusage` подпроцессом (`run_ccusage`) и сравнивает
  с результатом `parse.collect()` + `pricing.load()` по каждому компоненту
  токенов (`COMPONENTS`) и по стоимости, с порогом расхождения в процентах.

## Не наступать на грабли парсинга

Всё ниже — источник тихих искажений цифр, уже отловленных на реальных данных
(подробности и цифры расхождений — в README.md, раздел «Ловушки парсинга»):

1. Группировка по часам — **локальная таймзона** (`astimezone()`), не UTC.
2. Claude: дедуп записей по `requestId` (fallback `message.id`), берётся
   максимум — стриминг пишет и промежуточную, и финальную запись одного events.
3. Claude: сабагенты лежат в `<проект>/<sessionId>/subagents/agent-*.jsonl` —
   нужен **рекурсивный** glob, иначе теряется ~70% файлов. Имя агента — только
   в поле `attributionAgent` этих файлов.
4. Codex: `total_token_usage` кумулятивен, суммировать нужно
   `last_token_usage`; дедуп — по кумулятивному (монотонно растущему) ключу.
5. Codex: `input_tokens` уже включает `cached_input_tokens` — при разбивке по
   компонентам кэш нужно вычитать, иначе он учтётся дважды.
6. Anthropic: кэш с TTL 1h тарифицируется иначе, чем 5m (у sonnet-5 $4.00
   против $2.50 за Mtok) — TTL смотрится в
   `usage.cache_creation.ephemeral_1h_input_tokens`.
7. Codex: модель — не в `session_meta`, а в первой записи `turn_context`.
8. Codex: `payload.source` у сабагентов бывает объектом
   (`{"subagent": {"other": "..."}}`), а не только строкой.
9. Worktree-воркеры оркестратора (`<worktrees>/<проект>/<проект>-NN`)
   схлопываются к родительскому проекту **по пути**, не отрезанием суффикса
   `-NN` (иначе ломаются проекты вида `project-3310`).

## Границы применимости

- Gemini не поддерживается (логи не содержат usage-данных).
- Стоимость считается по прайс-листу API, а не «сколько списано с карты» —
  если модель идёт по подписке, дашборд честно показывает её отдельно, а не
  как $0, смешанный с реальными нулями.
- Fast-режим Codex не воспроизводится локально (нет признака speed в
  rollout-логах) — расчёт соответствует `--speed standard`.
