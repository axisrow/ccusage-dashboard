# ccusage-dashboard

Почасовой дашборд расхода Claude Code и Codex **в долларах** с разбивкой по
инструменту, модели, агенту и проекту. Один self-contained HTML, только stdlib,
без зависимостей.

Токены плохо отражают деньги — их четыре типа с разной ценой. У `claude-sonnet-5`
чтение кэша стоит $0.20 за Mtok, а вывод — $10.00: **разница в 50 раз**. Поэтому
основная единица — доллары, а переключатель показывает токены, когда нужен объём.

Пример: три модели с почти одинаковым объёмом токенов.

| Модель | Токенов | Стоимость |
|---|---|---|
| модель A (дорогая) | ~50 млн | **$120** |
| модель B (средняя) | ~50 млн | **$38** |
| модель C (по подписке) | ~50 млн | **$2** |

Почти одинаковый объём — и разница в цене в 30 раз. По токенам эти три строки
выглядели бы близнецами.

## Зачем не просто `ccusage`

`ccusage` не даёт нужных разрезов: `session --json` возвращает `lastActivity` без
проекта и без почасовой шкалы, `blocks -n 1` даёт почасовую сетку, но агрегированную
по всему сразу.

Главное — **`ccusage` сканирует все логи целиком (~6 ГБ) независимо от `--since`**:
49 с за два дня, больше двух минут за полный период. Свой парсер читает всю историю
Claude за ~1.3 с и Codex за ~1.7 с, поэтому кэш не нужен: пересчёт с нуля дешевле
чтения кэша.

Точность проверена: расхождение с `ccusage` **−0.01 % по Claude и 0.00 % по Codex**
(2–3 августа 2026, по всем компонентам токенов).

## Использование

```bash
./pricing.py --refresh                       # ОДИН РАЗ: собрать ставки моделей
./report.py --since 20260801 --open          # дашборд за период, открыть в браузере
```

```bash
./report.py --since 2026-08-01 --until 2026-08-03 --out dash.html
./report.py --since 20260801 --tool codex    # только один инструмент

./parse.py --stats                           # сводка в терминал, без HTML
./parse.py --since 20260801 --json           # плоские записи в JSON

./pricing.py --show                          # текущие ставки и их источник
./verify.py --since 20260802 --until 20260803   # сверка с ccusage (медленно, минуты)
```

Даты понимаются в обоих форматах: `20260801` и `2026-08-01`, границы включительно.
Ставки кэшируются в `rates.json`; обновляйте их при появлении новых моделей.

## Откуда берутся цены

Прайсинг не захардкожен — он быстро устаревает. Источники, в порядке доверия:

1. **LiteLLM** — тот же прайсинг, что использует сам `ccusage`. Учитывается TTL
   кэша: запись с ttl=1h дороже 5m (у sonnet-5 $4.00 против $2.50). Без этого
   расчёт занижался на ~9 %.
2. **Подгонка из `ccusage`** методом наименьших квадратов — для моделей, которых
   нет в LiteLLM под этим именем (`glm-5-turbo`). Сходится с невязкой ~0 %.
   К моделям Anthropic НЕ применяется: там TTL-кэш и мало уравнений, МНК даёт
   абсурд (в тестах — $28539 за Mtok input).
3. **`$0`** — только если цены нет в LiteLLM И `ccusage` стабильно (не менее трёх
   дней) отдаёт ноль. Одного нулевого дня мало: так же выглядит и просто
   отсутствие прайсинга. Проверено на `claude-opus-5` — он показывал $0, пока
   LiteLLM не знал новую модель, а после обновления там оказались сотни долларов.
   Поэтому цена из LiteLLM всегда приоритетнее нуля от `ccusage`.

Модель, для которой ставку получить не удалось, **не считается бесплатной**: её
объём выносится в отдельную строку «без прайсинга» под плитками, чтобы «$0» нельзя
было спутать с «цена неизвестна». Так, у `gpt-5.3-codex-spark` в LiteLLM есть
запись, но нет полей цены (модель подписки ChatGPT) — её токены видны, а деньги нет.

Точность: по Claude расхождение с `ccusage` **0.00 %** (02–03.08), по Codex —
**0.1 %** (03.08).

**Fast-режим Codex не учитывается.** `ccusage codex` по умолчанию работает в режиме
`auto` и удваивает цену turn-ов, которые счёл «быстрыми», но признака speed в
rollout-логах нет — воспроизвести это решение локально нечем. Поэтому стоимость
Codex здесь соответствует `--speed standard` и может быть занижена, если вы
работали в fast-режиме (на 03.08 разница составила 2 %).
`verify.py` сверяется именно со `standard`, чтобы сравнение было честным.

## Что показывает

- **Расход в среднем за активный час** — основная метрика. Считается по часам с
  ненулевым расходом. Делить на все календарные часы бессмысленно: ночные простои
  размажут цифру в ноль. Рядом показан и календарный средний — на реальных данных
  разница почти полуторакратная.
- Почасовые столбики с накоплением по выбранному измерению и линией среднего.
- Сводная таблица: стоимость, доля, расход за активный час и **вторая единица**
  рядом — так видно, что миллиард токенов из подписки стоит $0.

Измерений четыре: инструмент, модель, агент, проект; переключатель единиц — `$` и
`токены`. Серии сортируются по стоимости, их не больше восьми — остальное
сворачивается в «Прочее», и подвал сообщает, сколько значений туда попало.

## Ловушки парсинга

Всё ниже проверено на реальных данных — каждый пункт молча искажает цифры.

1. **Локальная таймзона, не UTC.** `ccusage` группирует по локальной дате.
   Фильтрация по UTC-срезу давала −17.5 %, переход на `astimezone()` — +0.1 %.
2. **Дедуп Claude по `requestId`.** 64 % идентификаторов встречаются 2+ раз
   (стриминг пишет промежуточную и финальную запись). Без дедупа завышение в
   1.58 раза. Дубли несут одинаковые значения, поэтому берётся максимум.
   Fallback-ключ, если `requestId` нет: `message.id`.
3. **Подагенты Claude лежат в отдельных файлах** —
   `<проект>/<sessionId>/subagents/agent-*.jsonl`, на реальных данных это была
   примерно две трети всех файлов. Нерекурсивный glob потерял бы ~70 % данных.
   Имя агента — в `attributionAgent`, и оно есть только в этих файлах.
4. **У Codex `total_token_usage` кумулятивен** — суммировать надо
   `last_token_usage`. Но и он дублируется: последняя запись повторяется, поэтому
   дедуп идёт по кумулятивному ключу, который монотонно растёт.
5. **`input_tokens` у Codex включает `cached_input_tokens`** — при раскладке по
   компонентам кэш нужно вычесть, иначе он посчитается дважды.
6. **Кэш с TTL 1h дороже 5m.** У Anthropic запись кэша тарифицируется по-разному
   в зависимости от TTL — у sonnet-5 $4.00 против $2.50 за Mtok. TTL виден в
   `usage.cache_creation.ephemeral_1h_input_tokens`; без его учёта стоимость
   занижалась примерно на 9 %.
7. **Модель Codex не в `session_meta`**, а в первой записи `turn_context`.
8. **`payload.source` у Codex бывает объектом** для подагентов
   (`{"subagent": {"other": "<имя-агента>"}}`), а не только строкой.
9. **Worktree схлопываются к родительскому проекту.** Воркеры оркестратора живут в
   подкаталогах вида `<worktrees>/<проект>/<проект>-NN`; без схлопывания один
   проект рассыпается на десятки серий и почти половина расхода уезжает в
   «Прочее». Родитель берётся из пути, а не отрезанием суффикса `-NN` — иначе
   пострадали бы проекты с числом в имени вроде `project-3310`.

## Границы применимости

- **Gemini** usage-данных в логи не пишет — не поддерживается.
- **OpenCode** формат имеет (`~/.local/share/opencode`), но в просмотренных сессиях
  токены нулевые — не включён.
- Стоимость считается **по прайс-листу API**. Если модель идёт по подписке,
  `ccusage` отдаёт по ней $0 — дашборд это уважает и показывает такие модели
  отдельной строкой. То есть сумма отвечает на вопрос «сколько бы это стоило по
  API», а не «сколько списано с карты».
- Как и любой локальный инструмент, парсер видит только то, что записано в логи на
  диске. Эфемерные подагентские треды `codex app-server` расходуют лимит, но
  rollout-файл не пишут (openai/codex #30918, #31125) — их не видит ни этот
  дашборд, ни `ccusage`.

## Файлы

| Файл | Назначение |
|---|---|
| `parse.py` | параллельный парсер логов, дедуп, локальное время |
| `pricing.py` | ставки моделей: LiteLLM, подгонка из `ccusage`, подписка |
| `report.py` | агрегация по часам и рендер HTML |
| `verify.py` | сверка токенов и стоимости с `ccusage` |
| `rates.json` | кэш ставок (создаётся `./pricing.py --refresh`) |

Цвета графика — категориальная палитра, проверенная на различимость при дальтонизме
в обеих темах (светлая и тёмная). Порядок слотов менять нельзя: именно он
обеспечивает разделение соседних серий.
